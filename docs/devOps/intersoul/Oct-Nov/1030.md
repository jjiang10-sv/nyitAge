In Kubernetes, pods access each other using services which act as a stable networking endpoint, regardless of the individual IPs of the pods within the service. Here’s how it works:

1. Service Discovery Using CoreDNS

Kubernetes uses CoreDNS as its DNS service to resolve internal service names to IP addresses. When a service is created, Kubernetes automatically updates CoreDNS with an entry for that service. This allows any pod in the cluster to access the service by name.

For example, if you have a service called sampletest in the keda namespace, it can be accessed by other pods in the same namespace as sampletest, or from different namespaces as sampletest.keda.

2. CoreDNS Resolution Process

When a pod tries to access sampletest.keda, here’s how CoreDNS resolves it:

	•	ClusterIP Resolution: Kubernetes assigns each service a unique ClusterIP (an internal IP within the cluster). CoreDNS maps the service name (e.g., sampletest.keda.svc.cluster.local) to this ClusterIP.
	•	When a pod makes a request to sampletest.keda.svc.cluster.local, CoreDNS resolves this name to the ClusterIP of the service, which in turn directs traffic to the appropriate pod(s) behind the service.

3. CoreDNS Configuration

CoreDNS has a configuration file, usually located in a ConfigMap (coredns ConfigMap in the kube-system namespace), where it’s set up to handle svc.cluster.local as a DNS zone. By default, it forwards DNS queries matching this domain to the appropriate service IPs within the cluster.

Here’s an example of a CoreDNS configuration section for Kubernetes:

.:53 {
    errors
    health
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}

4. Service Types and Accessing Pods

The way CoreDNS resolves services depends on the service type:

	•	ClusterIP (default): Resolves to an internal IP, only accessible within the cluster.
	•	NodePort: Exposes the service on each node’s IP at a static port.
	•	LoadBalancer: Creates an external IP using a load balancer, accessible outside the cluster.
	•	Headless Service: If a service is set as headless (clusterIP: None), DNS resolves the service name to the actual pod IPs directly. This is useful for stateful applications needing direct pod access.

By combining CoreDNS and services, Kubernetes provides a flexible, dynamic, and reliable way for pods to locate and communicate with each other.

By default, Amazon EKS uses Amazon VPC CNI (Container Network Interface) plugin, also known as amazon-vpc-cni-k8s. This CNI plugin allows pods running on EKS to have IP addresses within the VPC, making them part of the VPC network. Here are some key aspects of the Amazon VPC CNI:

	1.	VPC IP Allocation: Each pod receives an IP address from the VPC subnet, making it natively accessible within the VPC without needing NAT or other networking tricks.
	2.	Elastic Network Interfaces (ENIs): The CNI assigns IP addresses to pods by allocating them from ENIs attached to the worker nodes. Each ENI can support multiple IP addresses, depending on the instance type.
	3.	Scaling and IP Limits: The maximum number of IP addresses (and therefore pods) on a node depends on the instance type, which determines the maximum number of ENIs and IP addresses per ENI.
	4.	Network Policies: While the Amazon VPC CNI plugin allows pod-to-pod and pod-to-service networking, it doesn’t support native Kubernetes NetworkPolicy. To implement network policies, you can use additional tools like Calico, which can operate alongside the VPC CNI to enforce security policies within the cluster.

You can confirm that the Amazon VPC CNI plugin is being used by looking for the aws-node DaemonSet in the kube-system namespace:

kubectl get daemonset aws-node -n kube-system

This DaemonSet manages the Amazon VPC CNI plugin on each node in the EKS cluster.

When a container inside a Kubernetes pod is stuck in a "back-off restarting failed" state while the pod itself is running, it usually indicates that the container has failed to start or keep running, possibly due to misconfigurations or runtime issues. Kubernetes will keep trying to restart the failed container in a loop. The pod will remain in a "running" state as long as at least one container is running, but you need to investigate why the other container(s) are failing.

### Steps to Troubleshoot and Fix

#### 1. Check Pod and Container Logs

Use `kubectl logs` to view the logs of the container that is failing to help diagnose the issue. Replace `pod-name` and `container-name` with the actual names of your pod and container.

```bash
kubectl logs <pod-name> -c <container-name>
```

If you only have one container in the pod:

```bash
kubectl logs <pod-name>
```

This should give you some insight into why the container is failing (e.g., missing dependencies, misconfigurations, startup errors).

#### 2. Describe the Pod

You can use `kubectl describe pod` to get detailed information about the pod, including the events that have occurred. This will often show why a container is in a crash/restart loop.

```bash
kubectl describe pod <pod-name>
```

Look for events such as:
- **Failed to pull image** (ImagePullBackOff)
- **CrashLoopBackOff** (indicating continuous crashes)
- **Error in container startup** (e.g., missing environment variables or config files)

#### 3. Check Container Exit Codes

In the output of `kubectl describe pod`, check for the container’s exit code. Some common exit codes:
- `ExitCode: 1`: Indicates a general error (app crash).
- `ExitCode: 137`: Indicates that the container was killed, possibly due to an out-of-memory issue.
- `ExitCode: 126` or `127`: Command not executable or command not found, respectively.

#### 4. Check Resource Limits

If your container is being killed by Kubernetes, it might be due to exceeding resource limits. You can check the resource requests and limits set for the pod:

```bash
kubectl describe pod <pod-name>
```

Make sure your container has appropriate CPU and memory limits defined. If a container exceeds its limits, it can be killed by Kubernetes (OOMKilled).

#### 5. Review the Liveness and Readiness Probes

If you have configured **liveness** or **readiness** probes, they may be causing the container to restart if they are incorrectly set or if the container fails to pass the checks.

Check your deployment YAML or use `kubectl describe pod` to verify the probes:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
```

Ensure the probes are correctly set up and that the service they are probing is reachable and functional.

#### 6. Check Image Configuration

If there is an issue with the container image, such as an incorrectly tagged image, a missing image, or a corrupted image, the container may fail to start.

Verify the image in your deployment:

```yaml
image: my-container-image:latest
```

- Make sure the image exists in the repository.
- Make sure the tag is correct.
- Check if the image can run locally.

You can also try pulling the image manually on your local machine or node to check for any issues.

#### 7. Use `kubectl exec` to Investigate

If the container stays up for a short time before crashing, you can use `kubectl exec` to open a shell in the container and investigate further.

```bash
kubectl exec -it <pod-name> -c <container-name> -- /bin/sh
```

You can check logs, system configuration, or run diagnostic commands directly in the container before it crashes.

#### 8. Restart the Pod

If you're able to resolve the issue (e.g., by fixing a misconfiguration), you can delete the pod to restart it. Kubernetes will automatically recreate the pod:

```bash
kubectl delete pod <pod-name>
```

Alternatively, you can scale down the deployment to 0 and then back up:

```bash
kubectl scale deployment <deployment-name> --replicas=0
kubectl scale deployment <deployment-name> --replicas=1
```

This will cause Kubernetes to create a new pod with the updated configuration.

#### 9. Check Node Resource Limits

Sometimes the container may fail to start due to insufficient resources on the Kubernetes node itself (e.g., CPU or memory exhaustion). You can check the status of the node:

```bash
kubectl describe node <node-name>
```

Look for signs that the node is under pressure or out of resources.

### Summary

To fix a container in the "back-off restarting failed" state while the pod is running:
1. **Check logs** to identify the root cause.
2. **Describe the pod** to see events and exit codes.
3. **Check resource limits** to ensure the container is not running out of memory/CPU.
4. **Verify liveness/readiness probes** to ensure they're correctly configured.
5. **Confirm the container image** is valid and correctly tagged.
6. **Use kubectl exec** for debugging inside the container if it runs for some time.
7. **Restart the pod** after fixing the issue.

To remove multiple Custom Resource Definitions (CRDs) in batch that share a common pattern in their names, you can use a combination of `kubectl get` and `kubectl delete` commands with command substitution in a shell. Here's how you can do it:

### Using Shell Command

1. **Identify the Common Pattern**: Determine the common part of the CRD names that you want to delete.

2. **Use `kubectl get` with `-o name`**: Fetch the CRD names that match the pattern.

3. **Use `xargs` to delete them**: Pass the list of CRD names to the `kubectl delete` command.

### Example Command

For example, if you want to delete all CRDs that start with `example.`:

```bash
kubectl get crd -o name | grep '^customresourcedefinition.example.' | xargs kubectl delete
```

### Breakdown of the Command

- `kubectl get crd -o name`: Lists all CRDs by their names.
- `grep '^customresourcedefinition.example.'`: Filters the list to include only those CRDs that start with `customresourcedefinition.example.`.
- `xargs kubectl delete`: Takes the filtered list of CRDs and deletes them.

### Note

- **Caution**: This command will permanently delete the CRDs and any associated custom resources. Ensure you have backups or are certain about the deletion before running this command.
- You can modify the `grep` pattern to match the specific naming convention of the CRDs you want to delete. For instance, if they contain a certain substring or end with a specific suffix, adjust the pattern accordingly.

### Example for Substring Match

```bash

```

This will delete all CRDs with names containing `myresource`.

To check the resource capacity of your Kubernetes nodes, you can use the `kubectl describe nodes` command, which provides detailed information about each node, including its CPU and memory capacity. Here are a few different methods to get the information you need:

### Method 1: Describe Nodes

1. **Describe Nodes Command**:
   You can use the following command to get detailed information about all nodes:

   ```bash
   kubectl describe nodes
   ```

   Look for the `Capacity` and `Allocatable` sections, which will show the total resources available on each node.

### Method 2: Get Nodes Resource Summary

2. **Get Nodes Command**:
   A more concise way to view the capacity of all nodes is to use:

   ```bash
   kubectl get nodes -o=custom-columns=NAME:.metadata.name,CAPACITY:.status.capacity
   ```

   This command will output a summary of node names and their resource capacities, including CPU and memory.

### Method 3: Resource Metrics

3. **Metrics Server**:
   If you have the Metrics Server installed in your cluster, you can check the resource usage with:

   ```bash
   kubectl top nodes
   ```

   This will show the current resource usage of the nodes, including CPU and memory, and can help you understand how much capacity is being utilized.

### Method 4: Using `kubectl get` with JSONPath

4. **JSONPath Output**:
   If you want a more customized view of resource capacity, you can use JSONPath:

   ```bash
   kubectl get nodes -o=jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.capacity.cpu}{"\t"}{.status.capacity.memory}{"\n"}{end}'
   ```

   This command provides a tab-separated list of node names along with their CPU and memory capacity.

### Example Output

The output will look something like this:

```

node2   4          16Gi
```

- The first column shows the node name.
- The second column indicates the number of CPU cores.
- The third column indicates the total memory capacity in GiB.

These commands will help you assess the resource capacity of your Kubernetes nodes. Choose the method that best fits your needs based on whether you want detailed descriptions, summaries, or specific information.
